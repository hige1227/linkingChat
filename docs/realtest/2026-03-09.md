## 问题 1：`flutter_gen` 包找不到，l10n 导入路径错误

**阶段**：`flutter run -d chrome` 编译

**现象**：
```
Error: Couldn't resolve the package 'flutter_gen' in 'package:flutter_gen/gen_l10n/app_localizations.dart'
```
`app.dart` 和 `profile_page.dart` 均报错。

**原因**：新版 Flutter（3.22+）已废弃 `synthetic-package` 机制，l10n 生成的文件直接输出到 `lib/l10n/` 目录，不再生成虚拟的 `flutter_gen` 包。但代码中 import 路径仍然是旧版的 `package:flutter_gen/gen_l10n/app_localizations.dart`，导致编译器找不到该包。

**讨论**：有两种修法：
- A) 在 `l10n.yaml` 中加 `synthetic-package: false` 强制本地生成 → 但新版 Flutter 提示此参数已弃用且无效
- B) 直接把 import 改为相对路径指向 `lib/l10n/app_localizations.dart`

选择了方案 B，因为它兼容当前和未来的 Flutter 版本。

**修复**：
```dart
// app.dart — before
import 'package:flutter_gen/gen_l10n/app_localizations.dart';
// app.dart — after
import 'l10n/app_localizations.dart';

// profile_page.dart — before
import 'package:flutter_gen/gen_l10n/app_localizations.dart';
// profile_page.dart — after
import '../../../l10n/app_localizations.dart';
```

同时清理 `l10n.yaml`，移除废弃的 `synthetic-package` 行。

**文件**：
- `apps/mobile/lib/app.dart`
- `apps/mobile/lib/features/profile/pages/profile_page.dart`
- `apps/mobile/l10n.yaml`

## 问题 2：`json_annotation` 包缺失

**阶段**：`flutter run -d chrome` 编译

**现象**：
```
Error: Couldn't resolve the package 'json_annotation' in 'package:json_annotation/json_annotation.dart'
```
`UserProfile` 模型使用了 `@JsonSerializable()` 注解但 `pubspec.yaml` 中没有声明 `json_annotation` 依赖。

**原因**：`user_profile.dart` 使用了 `json_serializable` 代码生成模式（`@JsonSerializable()` + `part 'user_profile.g.dart'`），需要 `json_annotation` 运行时依赖和 `build_runner` + `json_serializable` 开发依赖。但 `pubspec.yaml` 中这三个都没有。`.g.dart` 文件是之前手动或在其他环境生成的，提交到了仓库但依赖声明遗漏。

**讨论**：有两种修法：
- A) 添加 `json_annotation` 到 `pubspec.yaml` → 首次尝试时因网络问题（pub.dev DNS 解析失败）无法下载
- B) 内联 fromJson/toJson 代码，完全移除对 `json_annotation` 的依赖

选择了方案 B，因为 `UserProfile` 只有 7 个字段，fromJson/toJson 逻辑简单，不值得引入额外依赖和代码生成工具链。

**修复**：重写 `user_profile.dart`，移除 `import 'package:json_annotation/json_annotation.dart'`、`@JsonSerializable()` 注解和 `part 'user_profile.g.dart'` 指令，将 `.g.dart` 中的 fromJson/toJson 逻辑直接内联到类中。删除 `user_profile.g.dart` 文件。

**文件**：

## 问题 3：`dio.patch()` 位置参数错误

**阶段**：`flutter run -d chrome` 编译

**现象**：
```
Error: Too many positional arguments: 1 allowed, but 2 found.
      await dio.patch('/api/v1/profile/me', {
```
`profile_provider.dart` 中 3 处 `dio.patch()` 调用均报错。

**原因**：Dio 5.x 的 `patch()` 方法签名为 `patch(String path, {dynamic data, ...})`，`data` 是命名参数而非位置参数。代码直接写成 `dio.patch('/path', {...})` 将 Map 作为第二个位置参数传入，Dart 编译器拒绝。

**修复**：3 处调用全部添加 `data:` 命名参数：
```dart
// before
await dio.patch('/api/v1/profile/me', { 'displayName': newName });
// after
await dio.patch('/api/v1/profile/me', data: { 'displayName': newName });
```

**文件**：`apps/mobile/lib/features/profile/providers/profile_provider.dart`（3 处修改）

## 问题 7：验证码输入后报"已过期"（双重提交）

**阶段**：手动测试 — 邮箱验证

**现象**：输入正确的 6 位验证码，显示"验证码已过期"。Chrome DevTools 网络面板显示了两次 `POST /api/v1/auth/verify-email` 请求（均返回 400）。

**原因**：`verify_email_page.dart` 的 `onChanged` 回调在检测到 6 位时立即调用 `_verify()`。由于 Flutter 的 `onChanged` 可能在短时间内连续触发（如焦点变化、自动填充等），导致 `_verify()` 被调用两次。第一次请求成功消耗了验证码，第二次请求时验证码已被删除，服务端返回"已过期"。但由于第二次的错误响应覆盖了第一次的成功状态，用户看到的是"已过期"。

**修复**：添加同步防护标志 `_verifyInProgress`，在 `_verify()` 函数入口处立即设置为 `true`（在 `setState` 之前），防止并发调用：
```dart
bool _verifyInProgress = false;

Future<void> _verify() async {
  if (_isLoading || _verifyInProgress) return;
  _verifyInProgress = true; // sync guard
  // ...
  finally { _verifyInProgress = false; }
}
```

**文件**：`apps/mobile/lib/features/auth/pages/verify_email_page.dart`

```typescript
return this.authService.verifyEmail(req.user.userId, body.code);

```

## 问题 10：验证码等待超时后 UI 卡死（QueuedInterceptor 死锁）

**阶段**：手动测试 — 邮箱验证（等待 10+ 分钟后输入验证码）

**现象**：注册后等待约 10 分钟再输入验证码，点击验证后 spinner 一直转圈，没有任何错误提示或反馈，UI 完全卡死。

**原因**：`AuthInterceptor` 继承了 Dio 的 `QueuedInterceptor`，当 access token 过期（15 分钟）时：
1. 请求发送 → 服务端返回 401
2. `onError` 拦截 401，调用 `refreshAccessToken()` 获取新 token
3. 用新 token 调用 `_dio.fetch(options)` 重试请求
4. **死锁**：`_dio.fetch()` 是同一个 Dio 实例，重试请求需要经过同一个 `QueuedInterceptor` 队列的 `onRequest`，但当前 `onError` 还在执行、队列锁未释放，导致重试请求被永久阻塞

这是 Dio `QueuedInterceptor` 的已知陷阱：在拦截器内部用同一 Dio 实例发请求会死锁。

**修复**：重试时创建一个不含拦截器的全新 Dio 实例，避免经过队列：
```dart
// before (deadlock)
final response = await _dio.fetch(options);

// after (no deadlock)
final retryDio = Dio(BaseOptions(
  baseUrl: _dio.options.baseUrl,
  connectTimeout: _dio.options.connectTimeout,
  receiveTimeout: _dio.options.receiveTimeout,
));
final response = await retryDio.fetch(options);
```

**文件**：`apps/mobile/lib/core/network/auth_interceptor.dart`

## 问题 12：好友 WS 事件通过 `device` 命名空间广播，客户端监听的是 `chat` 命名空间

**阶段**：手动测试 — Desktop ↔ Mobile 好友加好友后互发消息

**现象**：
1. Frank (Mobile) 加 Herry (Desktop) 为好友后，Desktop 端收不到 `friend:request` 事件
2. 接受好友请求后，`converse:new` 事件不到达任一客户端
3. 新 DM 会话的房间未加入，导致双方完全无法收发消息（**严重 Bug**）
4. Mobile 端需要手动重新打开会话才能收到消息

**原因**：`friends.service.ts` 中所有好友相关的 WS 广播都使用了 `broadcast.unicast()` 和 `broadcast.listcast()`，这两个方法在 `BroadcastService` 中硬编码使用 **`device` 命名空间**：

```typescript
// broadcast.service.ts — unicast/listcast 使用 device 命名空间
unicast(userId, event, data) {
  this.getNs('device').to(`u-${userId}`).emit(event, data);
}
listcast(userIds, event, data) {
  const rooms = userIds.map(id => `u-${id}`);
  this.getNs('device').to(rooms).emit(event, data);
}
```

而 Desktop 渲染进程和 Mobile 的 Socket.IO 客户端都只连接 `/chat` 命名空间，从不连接 `/device` 命名空间。因此所有好友事件（`friend:request`、`friend:accepted`、`friend:removed`、`converse:new`）对客户端完全不可见。

**修复**：
1. `BroadcastService` 新增 `chatUnicast()` 和 `chatListcast()` 方法，使用 `chat` 命名空间
2. `friends.service.ts` 中 6 处广播调用全部从 `unicast`→`chatUnicast`、`listcast`→`chatListcast`
3. `useChatSocket.ts` 新增 `converse:new` 事件处理器：重新拉取完整会话列表 + 自动加入新房间
4. 测试文件 `friends.service.spec.ts` 更新 mock 和断言

**文件**：
- `apps/server/src/gateway/broadcast.service.ts`
- `apps/server/src/friends/friends.service.ts`（6 处修改）
- `apps/server/src/friends/friends.service.spec.ts`（mock + 断言更新）

## 问题 13：`message:new` WS 广播缺少 `authorId` 字段

**阶段**：手动测试 — Desktop 端消息发送后自己的消息无法正确识别

**现象**：Desktop 端发送的消息没有已读回执（✓），消息排版与对方消息一致，无法区分"自己的消息"和"对方的消息"。

**原因**：`messages.service.ts` 构建 `message:new` WS 广播 payload 时，遗漏了 `authorId` 字段：

```typescript
// messages.service.ts L128-142 — 缺少 authorId
const messagePayload = {
  id: message.id,
  content: message.content,
  type: message.type,
  author: message.author,      // 只有嵌套的 author 对象
  // authorId: message.authorId  ← 缺失！
  converseId: message.converseId,
  ...
};
```

Desktop 端 `ChatThread.tsx` 用 `msg.authorId === currentUserId` 判断是否为自己的消息。`authorId` 为 `undefined` 时永远返回 `false`，所有消息都被当作"对方的消息"处理。

此外，消息发送者通过 REST 响应首先将消息添加到本地 store（此时包含 `authorId`），但随后 WS 广播的消息（不含 `authorId`）到达时，去重合并逻辑会用广播数据覆盖本地数据，导致 `authorId` 被覆盖为 `undefined`。

**修复**：在 `messagePayload` 中添加 `authorId: message.authorId`。

## 问题 17：Mobile 端发送者看到重复消息

**阶段**：手动测试 — Mobile (Ice) → Desktop (Herry) 发消息

**现象**：Mobile 端发送一条消息后，发送者会看到同一条消息出现两次。接收方（Desktop）只收到一条，显示正常。

**原因**：竞态条件（Race Condition）。`sendMessage()` 采用乐观更新策略：

1. 先在本地插入一条临时消息（ID 为 `temp_123456`）
2. 同时 POST 到服务器
3. 服务器保存后通过 WS 广播 `message:new`（带服务器分配的真实 ID）
4. REST 响应返回后，替换临时消息为服务器消息

问题在于：步骤 3 的 WS 广播有时比步骤 4 的 REST 响应**先到达**。此时 `message:new` handler 检查 `state.messages.any((m) => m.id == msg.id)` 进行去重——但本地只有 `temp_*` ID，服务器消息有真实 ID，去重失败，于是被当作"新消息"插入，造成重复。

**修复**：

在 `MessagesNotifier._setupSocketListeners()` 的 `message:new` handler 中增加三层去重逻辑：

1. **Server ID 去重**：如果已有相同 server ID 的消息，更新替换（原有逻辑）
2. **临时消息匹配**：如果存在 `temp_*` 开头且 `authorId` 相同的挂起消息，用服务器消息替换该临时消息
3. **新消息插入**：以上都不匹配，视为来自其他用户的新消息

```dart
// 2. Race condition: WS broadcast arrived before REST response.
//    Find and replace the pending optimistic message (temp_*) from same author.
final tempIdx = state.messages.indexWhere((m) =>
    m.id.startsWith('temp_') && m.authorId == msg.authorId);
if (tempIdx >= 0) {
  final updated = List<Message>.from(state.messages);
  updated[tempIdx] = msg;
  state = state.copyWith(messages: updated);
  return;
}
```

**结论**：**这是正确行为**，无需修复。

## 问题 20：Desktop 未读气泡切换标签后重新出现

**阶段**：手动测试 — Desktop 端标签切换

**现象**：Desktop 端阅读了会话列表后未读气泡消失，但切换到好友列表再切回来，未读气泡又出现了。

**原因**：`ChatPage.tsx` 在每次 mount 时都重新 fetch converses（`GET /api/v1/converses`），服务端返回的 `unreadCount` 是真实服务端值。而本地通过 `markConverseRead()` 仅在内存中将 `unreadCount` 置 0（未持久化到服务端），tab 切换导致 ChatPage unmount→remount→re-fetch，覆盖了本地的已读状态。

**修复**：
1. `ChatPage.tsx`：如果 store 已有 converses 数据则跳过 re-fetch
2. `chatStore.ts`：`setConverses()` 从简单覆盖改为智能合并，保留本地已标记为已读（`unreadCount: 0`）的会话状态

```typescript
// setConverses 智能合并逻辑
setConverses: (list) => set((state) => {
  const localReadSet = new Set(
    state.converses.filter((c) => c.unreadCount === 0).map((c) => c.id),
  );
  if (state.converses.length === 0) return { converses: list };
  return {
    converses: list.map((c) =>
      localReadSet.has(c.id) ? { ...c, unreadCount: 0 } : c,
    ),
  };
}),
```
