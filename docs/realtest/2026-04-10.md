# 真实测试记录 — 2026-04-10

> **测试范围**：Bot 回复消息消失问题深度调试 + 流式超时修复 + 错误兜底
>
> **测试环境**：Windows 11, Desktop (Electron + React), OpenClaw Gateway v2026.4.2 (本地进程模式), MiniMax-M2.7
>
> **测试方式**：Desktop UI 手动验证 + 渲染器/主进程控制台日志分析

---

## 一、问题复现

Bot DM 中发送消息，OpenClaw Agent 流式回复正常显示（含工具调用 + 文本），但回复完成后消息气泡消失。

表现：
1. 用户发送消息 → 用户消息持久化成功
2. Bot 流式回复出现 → 工具调用 ToolCallBlock 渲染 → 文本逐步输出
3. 流式完成 → **消息气泡消失**，对话列表中看不到 Bot 的回复

---

## 二、诊断过程

### 2.1 第一轮：添加诊断日志

在 `useOpenClawChat.ts` 的 persist/remove 流程中添加详细日志：

```
[useOpenClawChat] Stream complete. finalState= {...}
[useOpenClawChat] hasText= ... hasToolRecords= ...
[useOpenClawChat] Persisting to: ... content length: ...
[useOpenClawChat] Persist response: ...
[useOpenClawChat] Removing streaming message: ...
```

同时在 `chatStore.ts` 的 chunk 处理中增加 error 类型日志：

```
[ChatStore] chunk: error text= ... tool= ... input= ... output= ...
```

### 2.2 第二轮：抓到关键证据

**渲染器控制台输出**：

```
[ChatStore] chunk: error tool= undefined input= undefined output= undefined
[useOpenClawChat] Stream complete. finalState= {
  exists: true, status: 'error', textLen: 0, toolRecords: 0,
  converseId: 'cmnsytio8000ro3013t0ifz0b', botId: 'cmnsytio7000qo301m0espwkc'
}
[useOpenClawChat] finalState not done: error — no persist/local message
[useOpenClawChat] Removing streaming message: str-1775864953704-lir7
```

**关键发现**：
- `status: 'error'` — 流以错误状态结束，不是 `'done'`
- `textLen: 0` — 没有任何文本被接收
- `toolRecords: 0` — 没有工具记录

但**主进程控制台**仍在输出事件日志，说明 OpenClaw Agent 仍在工作（工具执行中）。

### 2.3 第三轮：定位超时根因

再次测试，渲染器控制台明确显示：

```
[useOpenClawChat] Stream error: Chat timed out after 30000ms
```

同时主进程日志显示 Agent 仍在执行工具调用和生成文本。

**根因确认**：

| 组件 | 超时配置 | 实际值 |
|------|----------|--------|
| WS 客户端 `REQUEST_TIMEOUT` | 默认 chat() 超时 | 30 秒 |
| IPC 流式处理器 | 传递给 chat() 的 timeout | 未传（用默认 30s） |
| 渲染器安全超时 `STREAM_TIMEOUT` | 外层兜底 | 120 秒 |

OpenClaw Agent 执行工具（如 `system.run` 查询桌面文件）+ LLM 推理，总耗时超过 30 秒。WS 客户端先触发超时，发送 `error` chunk，流提前关闭。Agent 的后续输出被丢弃。

## 三、问题链分析

```
Agent 开始执行 (0s)
  ├── lifecycle:start
  ├── tool:start (system.run)
  ├── tool:update (执行中)
  │
  ├── ← 30s: WS 客户端超时 → 发送 error chunk
  ├── ← 渲染器收到 error → status 设为 'error'
  ├── ← useOpenClawChat 检查 status !== 'done' → 不创建本地消息
  ├── ← removeStreamingMessage → 流式气泡消失
  │
  ├── tool:result (Agent 仍在工作，但 renderer 已关闭)
  ├── assistant:text (Agent 输出文本，但 renderer 已关闭)
  └── lifecycle:end (Agent 完成，但无人接收)
```

两个 bug 叠加导致消息消失：
1. **超时太短**：30 秒不够 Agent 完成工作
2. **error 状态无兜底**：流以 `error` 结束时，不创建任何本地消息，直接删除流式气泡

## 四、修复

### 4.1 修复 1：增加流式 chat 超时到 120 秒

**文件**：`apps/desktop/src/main/ipc/openclaw.ipc.ts`

```typescript
// 修复前
for await (const chunk of client.chat(message, { sessionKey })) {

// 修复后：显式传递 120 秒超时，与渲染器 STREAM_TIMEOUT 对齐
for await (const chunk of client.chat(message, { sessionKey, timeout: 120_000 })) {
```

**理由**：Agent 执行工具 + LLM 推理可能需要 30-90 秒，120 秒足够覆盖大部分场景。

### 4.2 修复 2：error 状态兜底 — 创建本地错误消息

**文件**：`apps/desktop/src/renderer/hooks/useOpenClawChat.ts`

```typescript
// 修复前：error 状态直接跳过，不创建任何消息
} else {
  console.warn('[useOpenClawChat] finalState not done:', finalState?.status);
}

// 修复后：error 状态也创建本地消息，确保用户看到错误原因
} else if (finalState?.status === 'error') {
  const errorText = finalState.errorText || 'Unknown error';
  console.warn('[useOpenClawChat] Stream error:', errorText);
  useChatStore.getState().addMessage(converseId, {
    id: `local-${requestId}`,
    converseId,
    authorId: botId,
    content: `⚠ ${errorText}`,
    type: 'TEXT',
    createdAt: finalState.createdAt,
    updatedAt: new Date().toISOString(),
    author: { id: botId, username: 'Bot', displayName: 'Bot' },
  } as any);
}
```

**效果**：
- 即使流超时或出错，用户也会看到类似 `⚠ Chat timed out after 30000ms` 的错误消息
- 消息不会静默消失
- 用户知道需要重试

### 4.3 修复 3：增强 chatStore 错误日志

**文件**：`apps/desktop/src/renderer/stores/chatStore.ts`

```typescript
// 修复前：error chunk 不记录 text 字段
console.log('[ChatStore] chunk:', chunk.type, 'tool=', chunk.tool, ...);

// 修复后：记录 text 字段（包含错误原因）
console.log('[ChatStore] chunk:', chunk.type, 'text=', chunk.text?.slice(0, 200), 'tool=', chunk.tool, ...);
```

## 七、经验总结

1. **流式系统的超时需要端到端对齐**。WS 客户端默认 30 秒、IPC 未传超时、渲染器 120 秒 — 三层不一致导致中间层先断开。修复后统一为 120 秒。

2. **error 状态必须有用户可见的兜底**。之前的代码只处理 `status === 'done'`，error 直接跳过导致流式气泡被移除但无替代消息。任何结束状态（done/error）都应确保消息可见。

3. **诊断日志是定位问题的关键**。添加 `finalState` 完整打印后，立即发现 `status: 'error'` 而非预期的 `'done'`，定位到超时是根因。之前的日志只记录了事件流，缺少最终状态检查。
