# 真实测试记录 — 2026-04-08

> **测试范围**：OpenClaw 工具调用可见性 + Bot 回复稳定性 + 启动连接可靠性
>
> **测试环境**：Windows 11, Desktop (Electron + React), OpenClaw Gateway v2026.4.2 (全局安装, 本地进程模式), MiniMax-M2.7
>
> **测试方式**：Desktop UI 手动验证 + OpenClaw session 日志分析

## 一、OpenClaw 工具调用事件不可见

### 1.1 问题

Bot DM 中让 Agent 执行命令（如"列出桌面文件"），Agent 内部调用了 `system.run` 工具，但 Desktop UI 只显示最终文本回复，看不到工具调用过程。`ToolCallBlock` 组件已创建但从未渲染。

### 1.2 原因

OpenClaw Gateway WS 协议的**客户端能力声明机制**：connect 握手时需声明 `tool-events` capability，Gateway 才会转发 tool 事件。

```typescript
// openclaw-ws-client.ts 第 373 行
caps: [],   // ← 空数组，未声明 tool-events
```

Gateway 检查 `hasGatewayClientCap(client?.connect?.caps, 'tool-events')`，未声明则不注册到 `toolEventRecipients`，tool 事件不转发。

`~/.openclaw/openclaw.json` 已有 `verboseDefault: "full"`（控制 tool result 详细程度），但 `caps` 才是开关。

### 1.3 修复

```typescript
caps: ['tool-events'],  // 声明 tool-events 能力
```

**文件**：`apps/desktop/src/main/services/openclaw-ws-client.ts`

## 二、Tool 事件字段解析不匹配

### 2.1 问题

声明 `tool-events` 后日志中可见 tool 事件流入，但 ToolCallBlock 仍不渲染。WS 客户端的解析逻辑与实际 OpenClaw 协议字段不匹配。

### 2.2 三处不匹配

| 位置 | 代码中 | 实际协议 |
|------|--------|----------|
| 工具名 | `data.tool` | `data.name`（如 `"exec"`） |
| 结果阶段 | `phase === 'end'` | `phase === 'result'` |
| 输出提取 | `data.output` | `data.result.details.aggregated` 或 `data.result.content[0].text` |

### 2.3 修复

```typescript
// 工具开始
const toolName = data.name || data.tool || '';

// 工具结果（phase 改为 'result'）
} else if (stream === 'tool' && data?.phase === 'result') {
  // 从嵌套结构提取输出
  if (data.result?.details?.aggregated != null) {
    output = String(data.result.details.aggregated);
  } else if (data.result?.content?.[0]?.text != null) {
    output = String(data.result.content[0].text);
  }
```

**文件**：`apps/desktop/src/main/services/openclaw-ws-client.ts`

### 2.4 验证结果

修复后 ToolCallBlock 正常渲染：
- 工具名（如 `exec`）+ 命令输入（如 `$ Get-ChildItem -Path ...`）
- 执行中显示 spinner
- 完成后可点击展开查看输出

## 三、Bot 回复消息消失

### 3.1 问题

流式回复完成后，Bot 的消息气泡有时会短暂消失再出现，或完全消失。

### 3.2 原因

streaming bubble 的生命周期有缝隙：

```
streaming 完成 → POST /bots/:botId/reply 持久化 → 等 800ms → 删除 streaming bubble
                                                    ↑
                                          期望 WS message:new 在此期间到达
                                          如果没到 → 消息消失
```

REST 响应中包含完整的 message 对象，但客户端**没有读取**，完全依赖 WS 事件的时序。

### 3.3 修复

读取 REST 响应，直接写入 store，不再依赖 WS 时序：

```typescript
const res = await fetch(`${API_URL}/bots/${botId}/reply`, { ... });
if (res.ok) {
  const savedMsg = await res.json();
  if (savedMsg?.id) {
    useChatStore.getState().addMessage(converseId, savedMsg);
  }
}
// 立即移除 streaming bubble（persisted message 已在 store 中）
useChatStore.getState().removeStreamingMessage(requestId);
```

后续 WS `message:new` 到达时，`addMessage` 按 id 去重合并，不会产生重复。

**文件**：`apps/desktop/src/renderer/hooks/useOpenClawChat.ts`

## 四、MiniMax API 间歇性空回复

### 4.1 问题

连续对话后，Bot 完全无回复。UI 上消息静默消失，无任何错误提示。

### 4.2 诊断过程

查看 OpenClaw session JSONL 日志，发现空回复记录：

```json
{
  "role": "assistant",
  "content": [],
  "usage": {"input": 0, "output": 0, "cacheRead": 0, "cacheWrite": 0, "totalTokens": 0},
  "stopReason": "stop",
  "responseId": ""
}
```

关键证据：
- `input: 0, output: 0` → API 调用根本没执行
- `responseId: ""` → 无实际 API 响应
- 正常调用的 token 用量仅 ~14K / 200K (7%)，远未触及 context 上限

### 4.3 结论

**不是 context 溢出，是 MiniMax API 间歇性故障**（可能是限流、服务端错误、或网络问题）。

初始误判为 session context 撑大导致，但实际数据表明 context 用量极低。OpenClaw 系统提示占 ~13K tokens（固定开销），用户对话内容仅占 63 → 1,234 tokens。

### 4.4 修复（三层防护）

#### 层 1：空回复检测 + 错误提示

在 WS 客户端的 `lifecycle end` 处理中，检测是否有实际内容产出：

```typescript
const hasContent = chunks.some((c) => c.type === 'text' || c.type === 'tool_use');
if (!hasContent && data.phase !== 'error') {
  chunks.push({
    type: 'error',
    text: 'Agent returned empty response. Session context may be too large — try sending a new message.'
  });
}
```

**文件**：`apps/desktop/src/main/services/openclaw-ws-client.ts`

#### 层 2：自动 session reset + 重试

IPC 流式处理器检测到空回复 error 后，自动调用 `sessions.reset` 清空 session，用新 session 重试同一条消息。对 renderer 透明。

```typescript
if (chunk.type === 'error' && !hasContent && !emptyRetried && chunk.text.includes('empty response')) {
  emptyRetried = true;
  await client.resetSession(sessionKey);
  await runStream();  // 重试
  return;
}
```

**文件**：`apps/desktop/src/main/ipc/openclaw.ipc.ts`

WS 客户端新增 `resetSession` 方法，调用 OpenClaw 的 `sessions.reset` WS 方法：

```typescript
async resetSession(sessionKey: string): Promise<void> {
  await this.request('sessions.reset', { key: `agent:main:${sessionKey}`, reason: 'new' }, 10_000);
}
```

**文件**：`apps/desktop/src/main/services/openclaw-ws-client.ts`

#### 层 3：OpenClaw 配置优化（预防性）

虽然当前问题不是 context 溢出，但为未来对话量增长预防性配置：

```json
{
  "agents": {
    "defaults": {
      "contextTokens": 150000,
      "compaction": {
        "reserveTokensFloor": 24000,
        "notifyUser": true
      },
      "contextPruning": {
        "mode": "cache-ttl",
        "ttl": "5m",
        "keepLastAssistants": 3,
        "softTrim": { "maxChars": 4000, "headChars": 1500, "tailChars": 1500 },
        "hardClear": { "enabled": true, "placeholder": "[Tool output cleared]" }
      }
    }
  }
}
```

| 配置 | 作用 |
|------|------|
| `contextTokens: 150000` | Context window 上限设为原生 200K 的 75%，所有模型通用 |
| `compaction` | 到 ~126K tokens 时自动摘要压缩（保留语义，不丢上下文） |
| `contextPruning` | 实时裁剪旧 tool 输出（如大文件列表），保留最近 3 轮完整内容 |

注意：未配置 `session.reset.idle`（idle 超时清空 session），因为这会丢失所有上下文，对聊天 bot 不合适。Compaction（摘要压缩）才是正确方案。

**文件**：`~/.openclaw/openclaw.json`

## 五、Desktop 重启后 OpenClaw 连接失败

### 5.1 问题

重启 Desktop 后有时连不上 OpenClaw Gateway，日志显示：

```
[OpenClaw:Process] Process started but health check timed out
[OpenClaw:Process] Stopping PID=51104
[OpenClaw:Process] Graceful shutdown failed, force killing PID=51104
```

需要在 devtools 手动执行 `await window.electronAPI.connectOpenClaw()` 才能连上。

### 5.2 原因

`index.ts` 启动时只调用一次 `connectToGateway()`，失败后无重试。OpenClaw 在 Windows 上冷启动有时慢（30 秒健康检查超时），或上次进程未完全退出。

### 5.3 修复

启动时加重试逻辑（最多 3 次，间隔 5 秒）：

```typescript
const MAX_RETRIES = 3;
const RETRY_DELAY = 5_000;
for (let attempt = 1; attempt <= MAX_RETRIES; attempt++) {
  const status = await connectToGateway();
  if (status.connected) return;
  if (attempt < MAX_RETRIES) await new Promise((r) => setTimeout(r, RETRY_DELAY));
}
```

**文件**：`apps/desktop/src/main/index.ts`

## 六、OpenClaw WS 协议学习记录

通过本次调试积累的 OpenClaw v2026.4.2 协议知识：

### 6.1 Connect 握手

```json
{
  "method": "connect",
  "params": {
    "caps": ["tool-events"],
    "role": "operator",
    "scopes": ["operator.read", "operator.write"],
    "device": { "id": "...", "publicKey": "...", "signature": "..." }
  }
}
```

- `caps: ['tool-events']` — 声明后 Gateway 才会转发 tool 事件

### 6.2 Agent 事件流

| stream | phase | 含义 |
|--------|-------|------|
| `lifecycle` | `start` | Agent 开始执行 |
| `tool` | `start` | 工具调用开始（含 `name`, `args`） |
| `tool` | `update` | 工具执行中间结果（`partialResult`） |
| `tool` | `result` | 工具执行完成（含 `result.details.aggregated`） |
| `assistant` | — | 文本输出（累积全文，需客户端做 delta） |
| `lifecycle` | `end` | Agent 执行完毕 |

### 6.3 Session 管理方法

| WS 方法 | 作用 |
|---------|------|
| `sessions.reset` | 清空 session，开始新对话 |
| `sessions.compact` | 手动触发 session 压缩（摘要） |
| `sessions.delete` | 删除 session（含 JSONL 文件） |

### 6.4 配置要点

- `agents.defaults.contextTokens` — 全局 context window 上限（cap），对所有模型生效
- `agents.defaults.compaction` — 自动 compaction 配置
- `agents.defaults.contextPruning` — 实时裁剪旧 tool 输出
- `agents.defaults.verboseDefault: "full"` — tool 事件包含完整 result 数据

## 八、关键结论

1. **OpenClaw 工具事件需要 `caps: ['tool-events']` 声明**，否则对客户端不可见。`verboseDefault` 控制详细程度，`caps` 是开关。

2. **MiniMax API 存在间歇性空回复**，表现为 `input:0, output:0, responseId:""`。不是 context 溢出（实际用量仅 7%），是 API 端问题。代码层面的自动 reset + 重试是有效应对。

3. **Bot 回复消息消失的根因是 REST→WS 时序竞争**。直接从 REST 响应写入 store 而非依赖 WS 事件到达，彻底消除了这个问题。

4. **OpenClaw compaction 配置是预防性措施**。`contextTokens: 150000` (75%) 对所有模型合理——低于此上限的模型不受影响，高于此上限的模型在到达前自动摘要压缩（保留语义）。
