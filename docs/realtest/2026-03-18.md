## 二、远程设备控制（Test 8）

### 8.0 前置问题：设备 upsert 不更新 userId

**发现过程**：Desktop(ice) 登录后，API 查询 `GET /devices` 返回空。数据库中设备 `device-yehui-win32` 存在但属于 alice（上次在此机器用 alice 登录过）。

**原因**：`devices.service.ts` 的 `upsertDevice()` 方法 `update` 分支没有更新 `userId`。当同一台机器（相同 hostname → 相同 deviceId）用不同账号登录时，设备记录仍绑定旧用户。

```typescript
// Bug: update 分支缺少 userId
update: {
  name: payload.name,
  platform: payload.platform,
  status: 'ONLINE',
  lastSeenAt: new Date(),
  // userId 缺失!
},
```

**修复**：在 update 分支中加入 `userId`

```typescript
update: {
  name: payload.name,
  platform: payload.platform,
  status: 'ONLINE',
  lastSeenAt: new Date(),
  userId, // 修复: 换账号登录时更新设备归属
},
```

**文件**：`apps/server/src/devices/devices.service.ts:54-59`
**严重性**：🔴 高 — 换账号会导致设备控制完全不可用

### 9.x 发现问题 2：BOT_NOTIFICATION 消息在 Mobile 上只显示空白 ℹ️ 图标

**现象**：Supervisor 会话中的 BOT_NOTIFICATION 消息只显示蓝色 ℹ️ 图标，无标题、无描述文字。

**原因**：
- Mobile `NotificationCard` 组件完全依赖 `message.metadata` 字段渲染（`cardType`, `title`, `description`, `sourceBotName`）
- `supervisor.agent.ts` 创建 BOT_NOTIFICATION 消息时只传了 `content`，没传 `metadata`
- `CreateMessageDto` 中缺少 `metadata` 字段定义
- `messages.service.ts` 的 `create()` 未将 metadata 传给 Prisma

**修复**（4 个文件）：
1. `messages/dto/create-message.dto.ts` — 新增 `metadata?: Record<string, any>` 可选字段
2. `messages/messages.service.ts` — Prisma create 中传入 `dto.metadata`
3. `agents/impl/supervisor.agent.ts` — `sendNotification()` 构建 metadata（cardType: task_complete/error, title, sourceBotName, actions）
4. `bots/bot-communication.service.ts` — 跨 Bot 通知也补充完整 metadata（cardType: info, title, description, sourceBotName）

## 五、架构级集成点审计（A–H）

> 对 8 个复杂架构集成点进行代码级逐一验证，检查生产链路是否真正打通。

### A: OpenClaw Gateway 集成

**验证方式**：代码追踪 + API 调用

**发现**：
- `GatewayManagerService.startGateway()` 尝试 `spawn('openclaw')` 启动进程
- **二进制不存在** — `openclaw` 可执行文件未安装，`spawn` 立即报 ENOENT
- `waitForGatewayReady()` 设置 10 秒超时，超时后**默认假定启动成功**
- `POST /openclaw/gateway/start` 返回 `status: "running"`，但端口 18790 无任何服务监听
- Status API 谎报运行状态

**结论**：🔴 **功能完全不可用** — 二进制缺失 + 超时假阳性 + 状态 API 虚假。整个 OpenClaw 集成是"空壳"。

---

### B: Predictive 自动触发链路

**验证方式**：代码追踪（事件链路：`device.result.complete` → 最终执行）

**发现**：
- `device.result.complete` → `BotEventListener.handleDeviceResultComplete()` → `BatchTriggerService.addEvent(SUPERVISOR_AGENT_BOT_ID)` → 5 秒后 → `SupervisorAgent.handleEvent()` → 生成通知
- **`PredictiveService.analyzeTrigger()` 无任何生产调用者** — 虽然方法完整实现，但没有代码路径触发它
- 唯一调用入口是 `POST /ai/predictive/trigger`（测试端点），生产事件链不经过此处

**结论**：🔴 **Predictive 自动触发不存在** — 服务端逻辑完整但无生产触发路径。命令完成后只有 Supervisor 通知，无 Predictive 分析。

---

### C: @CodingBot 提及处理

**验证方式**：代码追踪（`AgentsModule.onModuleInit()` 注册逻辑）

**发现**：
- `onModuleInit()` 仅注册 `supervisorAgent`（`this.orchestrator.registerAgent(this.supervisorAgent)`）
- 无 `CodingBotAgent` 类存在
- Chat Gateway 的 `@` 提及解析会尝试查找 Bot → 发送到 Orchestrator → 但找不到 agent → `warn('Agent not found')` → 静默丢弃

**结论**：🔴 **@CodingBot 提及被静默丢弃** — 仅有 SupervisorAgent 注册，@CodingBot 无对应 Agent 处理。

---

### D: Predictive Execute 真实执行

**验证方式**：代码追踪（`PredictiveService.executeAction()` 实现）

**发现**：
- `executeAction()` 仅做 DB 标记（将记录状态设为 ACCEPTED）并返回 action 对象
- **不发送任何命令到 Desktop 设备** — 没有调用 `device:command:send`、没有 WS 推送
- 客户端（Mobile/Desktop）收到 action 卡片上的"执行"按钮点击后，API 调用 `executeAction()`，但只得到一个确认对象
- 实际命令执行需要用户手动去远程设备控制界面重新输入

**结论**：🔴 **"执行"按钮实际无操作** — 仅 DB 记录变更，不触发真实命令下发。

---

### E: LLM Router 降级

**验证方式**：代码审查 + 单元测试（16 tests）

**发现**：
- `complete()` 方法：✅ DeepSeek 失败 → 自动降级 Kimi（反之亦然）
- Primary timeout 3 秒，Fallback timeout 10 秒
- 双方全挂 → 抛出 `All LLM providers failed`，调用方 catch 返回 null（不崩溃）
- ⚠️ `stream()` 方法**无降级逻辑** — 直接使用主 provider，失败不 fallback
- 当前所有 AI 服务（Whisper/Draft/Predictive）都使用 `complete()`，无生产代码使用 `stream()`

| 路由规则 | Provider |
|----------|----------|
| whisper / predictive / chat | DeepSeek（低延迟） |
| draft / complex_analysis | Kimi（高质量） |

**结论**：🟢 **降级机制工作正常**（`complete()` 路径）。`stream()` 缺少降级是潜在风险但当前无影响。

---

### F: 跨 Bot 通信入口

**验证方式**：引用追踪（`sendBotMessage()` + `routeViaSupervisor()` 所有调用者）

**发现**：
- `sendBotMessage()` 仅被 `POST /bots/test/cross-notify` 调用（测试端点）
- `routeViaSupervisor()` 仅被 `POST /bots/test/supervisor-route` 调用（测试端点）
- **无任何生产代码路径触发跨 Bot 通信**
- `bot:cross:notify` WS 事件：代码注释 `'Not needed on clients yet'`
- `bot:notification` WS 事件：Desktop/Mobile 均未监听
- 安全检查（rate limit 5/min、cycle detection、depth limit 3）逻辑完整

**结论**：🔴 **跨 Bot 通信整个功能不可用** — 服务端实现完整但：① 无生产触发入口 ② 客户端不监听 WS 事件。消息仅通过 DB 持久化可见。

---

### G: Supervisor 通知 5s 延迟

**验证方式**：代码审查 + 单元测试（3 tests）

**发现**：
- 事件链：`device.result.complete` → `BotEventListener` → `BatchTrigger.addEvent()` → 5s 后 flush → Supervisor → LLM → BOT_NOTIFICATION
- 纯 trailing-edge debounce：每个新事件重置 5 秒计时器
- ⚠️ **无最大等待时间** — 如果事件持续到达（间隔 < 5s），通知会无限延迟
- `onModuleDestroy()` 正确清理定时器
- 但最终通知推送的 `bot:notification` WS 事件**客户端未监听**（同 F 结论）

**结论**：🟡 **延迟机制本身工作** — debounce 逻辑正确，但：① 无最大延迟上限 ② 通知最终被客户端丢弃。
