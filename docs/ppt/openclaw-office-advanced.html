OpenClaw 科技进阶篇

协议实现 · 配置实战 · 扩展开发 · 调试排查
"入职培训只是开始。
真正的考验——在工程细节里。"
—— 关姐对新人的忠告

林小链入职 OpenClaw 科技已经一个月了。他熟悉了公司的基本运作——前台关姐的登记流程、项目经理阿管的工作闭环、会议室的管理规则。但这些都是"会用"的层面。

今天，CTO 叫他去了办公室。

CTO：小林，你熟悉了公司的基本流程。但如果你想真正掌控这套系统——不是"会用"，而是"能改、能调、能排障"——你需要搞懂四个东西：通讯协议的实现细节、配置文件的最佳实践、扩展开发的方法论、还有故障排查的套路。

于是，林小链开始了进阶之旅。

Part 1：协议实现深度

—— 通讯系统的底层逻辑

1.1
三种信封

阿管把林小链叫到会议室，在白板上画了一个大表。

阿管：小林，公司的内部通讯系统只传文本 JSON，不传二进制。所有消息分三种"信封"：
信封类型结构方向比喻
req{ type, id, method, params }你 → 公司你提交的申请表
res{ type, id, ok, payload }公司 → 你公司的审批回执
event{ type, event, payload, seq? }公司 → 你公司主动推送的通知
林小链：所以 req 和 res 是一问一答，event 是公司主动发过来的？
阿管：对。关键点是——req 的 id 和 res 的 id 必须配对。你发 id: "abc123" 的申请，回执也是 id: "abc123"。不配对就是串线了。
WS 帧只有文本帧，JSON 载荷。协议版本 PROTOCOL_VERSION = 3。Schema 源在 src/gateway/protocol/schema.ts（TypeBox）。副作用方法需要 幂等键（idempotencyKey），防止重复操作。

1.2
断线重连的艺术

周三下午，公司网络突然断了。林小链的会议室连接掉线。

林小链：（紧张）阿管！网络断了！我所有的对话记录还在吗？
阿管：（淡定）别慌。你的对话记录存在磁盘上（sessions.json + JSONL），不在内存里。断线只是丢了连接，数据没丢。重连就行。

阿管在白板上写下重连流程：

1. 检测断线（心跳超时 / WS error / close 事件） 2. 指数退避等待（1s → 2s → 5s → 10s → 30s → 60s，最多重试 100 次） 3. 重新走握手流程（challenge → connect → hello-ok） 4. 恢复上次活跃的 Session 5. 继续工作
林小链：为什么要指数退避？不能立刻重连吗？
阿管：（摇头）这是反脆弱设计——越失败越慢，而不是越失败越猛。最多重试 100 次。
林小链：那重连后，之前的消息怎么办？
阿管：对话数据存在磁盘上（sessions.json + JSONL），断线不丢失。重连后 Session 状态还在。event 帧有 seq 字段（序列号），理论上可以用来做断点续传，但 OpenClaw 官方文档没有明确说明自动重连后的 seq 回放机制——这部分需要实测验证。
重连策略：指数退避（1s → 2s → 5s → 10s → 30s → 60s），最多 100 次（源码 RECONNECT_DELAYS + MAX_RECONNECT_ATTEMPTS）。握手必须重新走。对话数据持久化在磁盘，断线不丢失。seq 字段存在但断点续传机制未经官方确认。
— · —
1.3
背压：消息太多怎么办

周五，林小链同时触发了三个 Agent 任务，事件通知疯狂涌入。

林小链：阿管！消息太多了，我的客户端处理不过来！
阿管：别慌。公司系统内部有消息队列（默认容量 1000 条），已经做了背压处理。Gateway 在消息堆积时会缓冲排队，不会把客户端冲爆。你不需要自己实现背压控制。
林小链：那客户端完全不用管？
阿管：Gateway 侧已经帮你扛了大部分压力。客户端侧只需要注意不要 block 主线程——lifecycle event（完成信号）优先处理；assistant event（流式文本）缓冲排队控制渲染节奏；tool event 可以 batch 更新。这不是背压问题，是渲染优先级问题。
Gateway 内置消息队列（MESSAGE_QUEUE_SIZE = 1000），超过队列限制时记录错误日志。Discord 等集成支持按账户配置 eventQueue.maxQueueSize。客户端不需要自己实现背压控制。

Part 2：配置实战手册

—— openclaw.json 最佳实践

2.1
规章制度总纲

CTO 把林小链叫到办公室，打开了一个文件：~/.openclaw/openclaw.json。

CTO：小林，这是公司的规章制度总纲。JSON5 格式——支持注释和尾逗号。改错了公司拒绝启动，不会静默忽略。

CTO 开始逐块讲解：

CTO：最关键的配置族有三个。第一，agents.defaults——员工默认行为。管脑容量（contextTokens）、性格（thinkingDefault）、工作时长（timeoutSeconds）、并行上限（maxConcurrent）。第二，compaction——文档精简策略。什么时候触发、保留多少近期内容、压缩前是否提醒存笔记。第三，session——会议室管理策略。重置周期、过期回收、磁盘预算。
配置文件用 JSON5 格式，但严格校验——未知键、类型错误、无效值会导致 Gateway 拒绝启动。唯一例外是根级 $schema 字段。
— · —
2.2
场景化配置模板

CTO 拿出三份配置模板，对应三种典型场景。

CTO：场景一：个人开发者本地使用。单用户、追求简单、不用审批。
{ agents: { defaults: { model: { primary: "minimax/MiniMax-M2.7" }, contextTokens: 200000, compaction: { enabled: true, reserveTokens: 16384, memoryFlush: { enabled: true }, }, // 不需要 contextPruning —— 个人使用对话量不大 }, }, session: { dmScope: "main", // 简单模式：所有对话一个 session reset: { mode: "daily", atHour: 4 }, }, }
CTO：场景二：多用户 SaaS 服务。需要隔离、需要安全、需要监控。
{ agents: { defaults: { model: { primary: "minimax/MiniMax-M2.7", fallbacks: ["deepseek/deepseek-chat"], // 故障转移 }, contextTokens: 200000, maxConcurrent: 8, // 多用户，提高并行 sandbox: { mode: "non-main", scope: "session", backend: "docker" }, compaction: { enabled: true, notifyUser: true, // 压缩时通知用户 identifierPolicy: "strict", }, contextPruning: { mode: "cache-ttl", // 开启工具结果裁剪 ttl: "5m", }, }, }, session: { dmScope: "per-channel-peer", // 严格隔离 reset: { mode: "daily", atHour: 4, idleMinutes: 120 }, maintenance: { mode: "enforce", pruneAfter: "7d" }, }, heartbeat: { every: "30m", target: "last", }, }
CTO：场景三：LinkChat 当前配置。本地进程、单用户、简化认证。
{ agents: { defaults: { model: { primary: "minimax/MiniMax-M2.7" }, contextTokens: 200000, compaction: { enabled: true, reserveTokens: 16384, memoryFlush: { enabled: true }, }, }, }, session: { dmScope: "per-channel-peer", reset: { mode: "daily", atHour: 4, idleMinutes: 120 }, maintenance: { mode: "enforce", pruneAfter: "7d" }, }, // --auth none：不验令牌，但验证设备身份 // 不需要 sandbox：本地单用户场景 // 不需要 heartbeat.target：默认 none，巡逻但不汇报 }
LinkChat 当前是场景三。可以改进的点：1）加 model.fallbacks 故障转移；2）开 contextPruning 减少工具结果膨胀；3）配置 heartbeat.target: "last" 让巡检结果主动推送。

Part 3：扩展开发

—— 技能、插件、定制化

3.1
写一本培训教材（SKILL.md）

CTO 给林小链布置了一个任务："给阿管写一个新的技能——让他在回答技术问题前，先搜索项目文档。"

阿管：（兴奋）小林，你要给我写培训教材了？来，我教你格式。

阿管在白板上写：

--- name: project-search description: Search project docs before answering tech questions user-invocable: true metadata: openclaw: requires: bins: ["grep", "find"] --- # Project Doc Search Before answering any technical question about the LinkChat project: 1. Use `grep` to search relevant files in the workspace 2. Read the top 3 most relevant files 3. Base your answer on the actual code, not guesses Always cite the file path and line number when referencing code.
阿管：扉页（frontmatter）用 YAML 格式。name 是技能名，description 是一句话说明，user-invocable: true 让你可以直接用 /project-search 调用。requires.bins 声明前置依赖——如果电脑上没有 grep 或 find，这个技能加载了也用不了。
林小链：写完放哪？
阿管：放进工作区的 skills/ 目录。优先级最高——只有我可以用。或者放进 ~/.openclaw/skills/，全公司的所有 PM 都能用。放好后下次开会我就自动学会了——不需要重启公司。
SKILL.md 格式：YAML frontmatter + Markdown 正文。关键字段：user-invocable（用户可调用）、disable-model-invocation（禁止 Agent 主动用）、command-dispatch: "tool"（绕过 Agent 思考直接分发到工具）。加载优先级：workspace > project > personal > global > built-in > extraDirs。
— · —
3.2
公司内部工具集成（Plugin Hooks）

林小链问阿管："能不能在顾问回复之前，自动加一段公司介绍？"

阿管：可以，这需要用插件钩子（Plugin Hooks）。公司系统在 PM 工作流的各个节点都埋了钩子——一共 28 个，覆盖模型调用、工具执行、消息流、子 Agent、Gateway 生命周期等。你可以在特定阶段插入自己的逻辑。最常用的有这些：
钩子时机能干什么
before_model_resolve选顾问之前强制指定用哪位顾问
before_prompt_build拼装提示词时注入额外的上下文或 system prompt
before_agent_reply顾问回复前拦截回复、返回合成内容、静默跳过
before_tool_call工具执行前修改工具参数或阻止执行
after_tool_call工具执行后修改工具返回值
agent_end任务结束时检查最终结果、记录日志
before_compaction文档精简前观察或修改精简策略
message_received收到消息时预处理入站消息
message_sending发出消息前拦截或取消发送
阿管：你说的"自动加公司介绍"，就用 before_prompt_build——在拼装提示词的时候注入一段 systemPrompt。或者用 before_model_resolve——根据问题类型强制指定用哪位顾问。
钩子共 28 个（源码 types.d.ts），上面列出最常用的 9 个。其他重要的还有：llm_input/llm_output（模型调用前后）、session_start/session_end（会话生命周期）、subagent_spawning/subagent_ended（子 Agent 管理）、gateway_start/gateway_stop（Gateway 生命周期）。
— · —
3.3
定制工作流程（Context Engine）

CTO 把林小链叫到办公室。

CTO：小林，你知道阿管每次开会前，是谁决定"带哪些资料"吗？
林小链：不是阿管自己决定的吗？
CTO：不是。是上下文引擎（Context Engine）决定的。它有四个生命周期钩子——Ingest（消息进来时存储索引）、Assemble（开会前拼装资料）、Compact（文档满了时精简）、AfterTurn（会开完后归档）。默认引擎是 "legacy"，但你可以通过插件替换成自己的。
林小链：替换整个引擎？那不是把核心逻辑都改了？
CTO：（微笑）这就是 OpenClaw 的设计哲学——默认好用，但允许替换。你不替换也行，替换了就能做定制化。比如你可以写一个 Context Engine，让阿管在开会时自动优先加载最近修改过的文件，而不是按时间顺序加载所有对话。
Context Engine 四钩子：Ingest（入库）→ Assemble（拼装）→ Compact（精简）→ AfterTurn（归档）。默认 "legacy"。可通过插件系统替换，实现定制化的上下文管理策略。

Part 4：调试与排查

—— 线上故障的急救手册

4.1
体检报告（Health Check）

某天下午，关姐的系统面板突然变红。

关姐：（皱眉）系统健康检查异常。谁去看一下？

林小链自告奋勇。阿管递给他一份排查清单：

# Step 1: 看 Gateway 是否活着 curl http://localhost:PORT/health # Step 2: 查看 Session 状态 openclaw sessions --json # Step 3: 检查最近心跳 # （RPC 方法 last-heartbeat） # Step 4: 查看在线设备列表 # （RPC 方法 system-presence） # Step 5: 查看模型调用状态 # （检查 provider 是否正常响应）
阿管：排查的第一步永远是分层定位——是网络层（WS 连接断了？）、是 Gateway 层（进程挂了？）、是 Agent 层（模型调用失败？）、还是数据层（Session 损坏了？）。从外到内，逐层排除。
排查四层模型：网络层（WS 连接/Tick）→ Gateway 层（进程/Health）→ Agent 层（模型/工具）→ 数据层（Session/文件）。先查外层再查内层。Health 端点能一次看到 Gateway 状态、WS 连接数、活跃 Session 数、最近心跳时间。
— · —
4.2
会议室状态检查

林小链用 openclaw sessions --json 查到了 Session 列表，但看不懂那些字段。

阿管：重点看这几个——sessionId（会议室当前编号）、updatedAt（最后活跃时间）、contextTokens（当前 context 占用）、compactionCount（精简了几次）。如果 contextTokens 接近 contextWindow（200K），说明快撑不住了——可能需要手动精简（/compact）。
林小链：那 Session 文件损坏了怎么办？
阿管：Session 数据在 ~/.openclaw/agents/<agentId>/sessions/ 目录下。sessions.json 是索引文件（K/V 映射），<sessionId>.jsonl 是对话记录（追加写入的 JSONL）。如果 sessions.json 损坏——最简单的办法是删掉它，Gateway 重启后自动创建空的。代价是丢失所有 Session 映射，但对话记录文件还在。
Session 文件结构：索引（sessions.json）+ 对话记录（<sessionId>.jsonl，树结构 id+parentId）。维护命令：openclaw status（概览）、openclaw sessions --json（列表）、/status（聊天中查 context 使用量）、/context list（查当前系统提示）。
— · —
4.3
通讯帧级别调试

有一次，林小链发了一条消息，阿管迟迟不回。蓝条没动静，绿条也没动静。

林小链：（焦虑）阿管，你是不是卡了？
阿管：（正在喝咖啡）没卡。我在等顾问回复，顾问还没回。
林小链：那怎么判断是"在等"还是"卡死了"？

阿管放下咖啡杯，认真地教他：

阿管：三层诊断。第一，WS 帧级别——用浏览器开发者工具的 Network 面板，过滤 WS 连接，看有没有数据在传输。如果完全没帧——是 WS 连接断了。如果有帧但都是 tick——是连接活着但 Agent 没在跑。第二，lifecycle 事件——看有没有收到 phase: "start"。如果没收到 start，说明任务根本没被接受。第三，模型调用链——如果 start 收到了但没有 assistant event，说明卡在模型调用上——可能是顾问超时或 rate limit。
林小链：那顾问超时了怎么办？
阿管：超时有两种。短超时（agent.wait 默认 30 秒）只影响等待方法，不影响实际执行。长超时（agents.defaults.timeoutSeconds 默认 600 秒 / 10 分钟）会强制终止 Agent 运行。如果顾问真卡了——你可以用 chat.abort 手动中止当前任务。
调试三层模型：1）WS 帧级别（Network 面板）；2）Lifecycle event（start/end/error）；3）模型调用链（assistant/tool event 交替）。chat.abort 可中止当前任务。Agent 运行超时默认 600 秒。
— · —
4.4
顾问调用失败排查

最让人头疼的问题——模型调用报错了。

阿管：小林，模型调用失败的排查有套路。先看错误类型——是认证错误（401/403）？限流错误（429）？参数错误（400）？还是服务器错误（5xx）？
错误类型HTTP 状态码原因处理
认证失败401/403API Key 无效/过期检查 Key 配置
限流429请求太频繁自动退避 + Key 轮换
参数错误400请求格式/参数有问题检查请求体
余额不足402账户没钱了充值（初始退避 5 小时）
模型不可用404/503模型名错误或下线检查模型 ID + fallbacks
阿管：关键规则——只有 rate-limit 类错误（429/资源耗尽）才会触发自动降级。认证失败、参数错误这类问题，降级到另一个顾问也没用——问题出在你这边，不在顾问那边。
林小链：那 Key 轮换是什么？
阿管：一个顾问可以配多把钥匙（API Key）。如果第一把被限流了，自动试第二把、第三把。轮换完了还是被限流，才降级到下一个顾问。Key 的优先级：OPENCLAW_LIVE_xxx（最高）→ xxx_API_KEYS（逗号分隔多个）→ xxx_API_KEY（单个）→ xxx_API_KEY_*（编号多个）。
最常见的"Unknown model"错误原因：1）模型 ID 写错了（大小写！）；2）Provider 没配置；3）API Key 没设置。排查顺序：先查 ID 拼写 → 再查 openclaw.json 的 models 配置 → 最后查环境变量。
